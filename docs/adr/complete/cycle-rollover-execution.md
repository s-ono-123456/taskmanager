# 論点: 週次サイクルの自動繰り越し（ロールオーバー）の実行方式

- 起票: 2026-09-13 / Linear風Cycles機能導入の一部（`docs/design/screen-board.md` 参照）
- 論点: 週境界（月曜0:00 JST）で、「今週」に属し未完了のタスクを次週へ自動的に繰り越す処理を、
  どの方式で実行するか。
- 状態: **案3採用・実装完了（2026-09-13）**

## 背景

本リポジトリは「外部通信は一切行わない」「単一バイナリで軽量」という既存方針を持ち、
現状`main.go`にアプリ独自の常駐処理（goroutine/ticker/cron）は一切存在しない
（`http.ListenAndServe`のみ）。grillingスキルでの確認により、未完了タスクの繰り越しは
自動で行いたい（手動操作は不要）との要件が確定している。

## 方針案

| 案 | 内容 | コスト | リスク | 状態 |
|---|---|---|---|---|
| 案1 | 外部（OS cron等）から定期的にHTTPエンドポイント（例: `POST /internal/cycles/rollover`）を叩く | 低（アプリ側実装は小さい） | デプロイ環境（単一コンテナ・外部通信なし方針）に別プロセス管理が必要になり運用が複雑化。既存の「単一バイナリ・外部依存最小化」方針に反する | 不採用 |
| 案2 | 画面表示（`GET /`）のたびに「週が変わっていれば繰り越しが必要か」を遅延評価し、その場で移動する | 低〜中 | 「cycle_start_dateの値そのものを更新する」という要件と噛み合わず、アクセスが無い間はDB上のデータが古いまま残り続ける | 不採用 |
| 案3 | アプリ内常駐goroutine（`time.Ticker`）で定期実行し、起動時にも1回同期実行する | 低（標準ライブラリのみで完結） | 週境界を跨いだままサーバーが停止していると繰り越しが遅れる→起動時1回実行で補完する | **採用** |

## 採用理由 / 検討経緯

単一バイナリ・外部通信ゼロという既存方針に最も自然に合致し、Go標準ライブラリ（`time.Ticker`）
のみで実装できる案3を採用した。本アプリにとって初めての常駐goroutine導入となるが、
`main.go`は元々グレースフルシャットダウンの仕組みを持たない（`log.Fatal`はdeferをスキップする）
ため、`context.Background()`を渡すだけの単純なfire-and-forget実装で既存の運用スタイルと
整合する。サーバー停止中に週境界を跨いでいた場合に備え、起動時にも同じロールオーバー処理を
1回同期実行する（ユーザー承認済みの補完）。タイムゾーンはJST固定オフセット
（`time.FixedZone`）で扱い、tzdataを持たないdistroless実行イメージでも
`time.LoadLocation("Asia/Tokyo")`への依存を避けている。
