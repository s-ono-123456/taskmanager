# 論点: 完了候補の承認UI（task-management-automation--c-completion-approval-ui）

- 起票: 2026-09-12 / 親タスク: `task-management-automation`（docs/adr/proposals/task-management-automation.md 参照）
- 論点: 完了判定(クローズ)は候補提示＋人間承認とする（自動クローズはしない。JIRAの誤クローズは
  気づかれにくく実害が大きいため）。この人間承認をどのUIで行うか。
- 状態: **採用済み（C3、2026-09-13。C2から変更）**

## 方針案

| 案 | 内容 | コスト | リスク | 状態 |
|---|---|---|---|---|
| C1 | Mattermost botのDMで個別に「クローズしてよいか」を都度確認 | 中 | 通知が多いと承認疲れが起きうる | 不採用 |
| C2 | 日次で「本日のクローズ候補一覧」を1メッセージにまとめて投稿し、リアクションで一括承認 | 中 | 即時性は下がるが承認負荷は低い | 不採用（2026-09-12採用 → 2026-09-13にC3へ変更） |
| C3 | ダッシュボードWebアプリ（既存のGo+sqlc+htmx実装）内に「クローズ要求一覧」画面を新設し、候補をDBに随時蓄積、ユーザーが任意のタイミングでまとめて承認・ステータス一括変更する | 中（既存ダッシュボードへの画面追加のみで済み、Mattermost bot・Webhook受信基盤は不要） | ユーザーが画面を開かないと承認が滞る（Mattermostのようなプッシュ通知が無く気づきにくい） | **採用**（2026-09-13） |

## 採用理由 / 検討経緯

### C2採用（2026-09-12、その後2026-09-13にC3へ変更）

当初は即時性より承認負荷の低さを優先し、日次まとめ＋リアクション一括承認（C2）を採用した。

### C3への変更（2026-09-13）

ユーザーから、C2（Mattermost日次まとめ＋リアクション承認）に代わり、パイロット実装済みの
ダッシュボードWebアプリ内に「クローズ要求一覧」画面を新設し、DBに候補を蓄積してユーザーが
任意のタイミングでまとめて承認する方式（C3）を採用する指示があり、C3へ変更した。

- **C2を不採用に変更した理由**: Mattermost bot・Webhook受信の実装（まだ着手していない
  collector/registrar側の基盤）が別途必要になり、パイロット実装済みのダッシュボードだけでは
  完結しない。
- **C3を採用した理由**: パイロット実装済みのダッシュボード（Go+sqlc+htmx）に画面を1つ
  追加するだけで完結し、Mattermost側の実装コストがかからない。通知の仕組みが無く
  ユーザーがダッシュボードを開かない限り承認が滞留するリスクはあるが、許容する。
- **ハイブリッドの余地（今後の検討候補、未決定）**: ダッシュボード側にクローズ要求一覧・
  一括承認UIを持たせつつ、Mattermostには「本日のクローズ候補が○件あります」という件数
  だけの軽量な通知を送る（詳細確認・承認操作自体はダッシュボードで行う）構成も、必要になれば
  追加で検討してよい。

C3自体はダッシュボード側にまだ実装しておらず、今後の実装タスクとして残っている
（`docs/design/task-management-automation.md`の「想定される次の一手」参照）。
